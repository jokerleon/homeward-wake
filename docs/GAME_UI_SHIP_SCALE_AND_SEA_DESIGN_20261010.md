# 游戏 UI、人船尺度与海况设计约束

2026-10-10，承接首版问题分析。用户明确指出：游戏 UI 必须有专门的图形美术与完整场景设计，不接受网页／CSS 风格的控件拼装；人物、船型和同时战斗人数必须一起考虑；水面应继续研究此前参考，包括雨、风与浪。

本轮完成参考复核、尺寸核对和工程排布示意，没有制作新的游戏 UI 美术资产，没有提交 H3／腾讯任务，也没有修改 Godot 运行代码。此前说明按钮显隐的文字表只能算功能清单，不能充当 UI 美术设计成果。

## 1. 游戏 UI 的交付形式

UI 以 v03 场景为共同美术环境：青灰海色、温暖木材和纸绢，少量旧铜／金色强调。图形细节应来自人物、航海、兵器与故事，而不是通用网页卡片、药丸按钮或大片纯色后台面板。装饰集中在重要轮廓和操作焦点，保证战场中央可以看清。

应先制作以下整屏美术稿及状态图，再接入 Godot；每张整屏稿展示正常游戏尺寸的背景、人物、图形控件、实际中文和交互焦点，不能用文字方框代替最终控件。

| 场景 | 固定布局与视觉任务 | 必须展示的状态 |
| --- | --- | --- |
| 港口探索 | 左下紧凑人物头像与生命；左上短任务；右上菜单；交互标记贴近实际 NPC | 空闲、靠近 NPC、当前可交谈、入队反馈 |
| 剧情对白 | 一侧独立半身立绘伸出下部对白框；姓名牌与纸绢式文字区；推进标记位于右下 | 当前说话人、另一人退暗、选项、跳过／回看入口、长短对白 |
| 航前改装／成长 | 船或角色仍是主要画面，两个选择用独立绘制的改装／技能图案解释收益 | 未选、选中、确认；确认后对实际角色／船的反馈 |
| 甲板部署 | 左下队员肖像可选择；场景内出现可部署边界和人物预览；右下开始战斗 | 合法位置、障碍／占位、无法到达、准备完成 |
| 甲板自动战斗 | 左下队员头像及冷却；右下预留选中者技能区；右上暂停；关键目标血条仅按需出现 | 普通战斗、选中慢速、技能就绪／冷却／不可用、倒地与破势 |
| 航行 | 左下船徽与船况；右上简洁罗盘、风向和菜单；航路指示落在海面 | 直航、转向、选中船、航点确认、进入遭遇 |
| 海战 | 延续航行布局，右下加入舷炮、弹种和齐射；装填在相应炮组图形上表达 | 装填中、可开火、切换待装弹、撤离、敌船停航和可接舷 |
| 暂停／失败 | 同套边框与字形，遮罩压低场景；有限的继续、重试、设置入口 | 当前焦点、确认与返回 |

布局位置是本轮提案，须在整屏美术稿里检验遮挡与鼠标移动距离。队员和船况尽量共用左下信息锚点，战斗指令共用右下锚点，避免跨场景来回寻找。若镜头主行动区压住某个角落，应一起调整镜头构图和 UI 安全区。

### 应作为游戏美术资源制作的内容

- 头像框、姓名牌、对白框的角饰／边条／底纹，选择框与确认印记。
- 技能、武器、弹种、炮组、舵令、风向、破势／压制／防护等可辨认图案。
- 血条外壳、生命填充、护盾／状态叠层、受伤残影、冷却遮罩及就绪提示。
- 游戏鼠标状态、人物选中标记、目的地标记、路线纹理、可达边界、部署轮廓和伤害预警。
- 按钮默认、聚焦、按下、禁用、冷却、就绪的完整状态图；不能只给一张正常按钮。

文字继续由引擎渲染，保证清晰和长短适配；美术资源负责轮廓、材质、图案与状态表现。使用图集、可伸缩边框和引擎动画组织，不以运行时代码画几个纯色矩形作为最终美术。

对话立绘独立生产，人物身份参考可以共用，不能从世界精灵放大裁切。新生成的合适图形素材遵守本地 H3 路线，参见 `CHARACTER_PRODUCTION.md`；图稿效果通过后再拆分资产，不能把整张不可操作的 AI 界面图直接贴进游戏。

## 2. 场景内反馈属于 UI 的一部分

| 玩家意图／状态 | 画面应如何反馈 | 数据约束 |
| --- | --- | --- |
| 选择人物 | 脚下出现精细绘制的选中轮廓，肖像框同步高亮；镜头适度聚焦 | 同一个选中状态驱动两处反馈 |
| 准备移动 | 到达点出现小型足迹／方向标记，路径绕过实际障碍；必要时显出附近可达边缘 | 使用实际导航路径，不画穿过桅杆的直线 |
| 点到不可走处 | 目的地标记变为不可达形状，短暂提示原因 | 不默默把目标夹到别的位置，也不允许越过不可达断层 |
| 布阵 | 可部署区域用轻薄的纹理与边界表达；落点显示人物预览 | 部署区必须是可达甲板的子集，避开障碍与他人占地 |
| 指定敌人 | 目标标记与可接敌位置清楚，必要时显示到攻击位的路径 | 近战站位可达且不与队友重叠 |
| 技能范围／蓄力 | 保留中心、边缘和落点的图形层级；前摇收束或进度明确 | 命中区域与提示同源，不用贴图大小独立决定伤害 |
| 人物受伤 | 生命变化与短促受击反馈；肖像状态始终可查 | 世界血条以选中、受伤、关键敌人为主，避免几十条常驻遮住甲板 |
| 海上航点 | 曲线航向预览、目的地与船艏方向标记 | 应考虑实际转向能力，不展示船无法执行的折线 |

普通移动不需要把整张甲板长期染绿或铺战棋格。全可走范围可在布阵／指挥时按需显示；障碍主要通过可见舱室、桅杆、船舷等空间形状表达。颜色之外配形状变化，避免状态只能靠红绿区分。

血条和角色标签要随镜头距离控制密度。选中者与当前危险目标保持清晰，次要单位可收起姓名；画面边缘提示用于暂时离开视野的重要单位。

## 3. 人船尺度：测量值、历史参照、游戏提案分别记录

### 当前测量事实

原运行船 `Godot/assets/quay-v03/merchant-ship-a.glb` 在此前转换中被设为约 16 个世界单位长。模型包围盒约长 16.0、宽 5.3，桅顶相对模型基准约 12.6。这个长度原本是港口样片的构图选择，不是经考据确定的船型规格。

现有战斗精灵按旧素材可见高度约 1.94 单位显示，老梁约 1.78。可见高度含头饰等画面范围，不能直接当成所有人物的解剖身高。

### 有来源的实船尺度参照

上海市政府 2010-07-01《中国航海博物馆专题新闻发布会》记载：馆内展示的明代福船复原实船设计总长 30.6 米、型宽 8.2 米、设计排水量 223.4 吨。[原文第二部分“文物收藏方面”末段](https://www.shanghai.gov.cn/nw9822/20200906/0001-9822_421809.html)。

这条资料用于建立 30 米级船舶与人物的数量级参照。它描述现代博物馆的复原实船；不据此推定所有明代福船尺寸，更不从排水量推算甲板战斗人数。当前生成船也不因长相相近就被认定为这个历史船型。

### 本游戏的船级和战斗人数提案

以普通成人约 1.8 米为初始尺度基准，人物占地半径约 0.35–0.4 米另行统一。头饰、武器和动作展开不改变基础碰撞体。人的世界尺度保持稳定，通过船型和镜头体现大小差异。

| 游戏内船级 | 代表尺寸，长×宽 | 规划的单船同时交战人数，敌我合计 | 示意排布 |
| --- | --- | --- | --- |
| 小型近海帆船 | 当前约 16×5.3 米 | 6–10，先以 8 人验证 | 4 对 4 |
| 中型航海船 | 提案约 24×7.2 米 | 12–20，先以 16 人验证 | 8 对 8 |
| 大型海船 | 提案约 34×9.4 米 | 24–36，先以 28 人验证 | 14 对 14 |

这里的“小／中／大”是项目内分级，不是历史船舶的统一法定分类。人数也是设计验证目标，尚未成为游戏规格或性能承诺；不等于船上全部水手、炮手、乘客和士兵的数量。可控制队伍人数仍单独确定，不能直接用上述总数扩大玩家操作负担。

### 当前 Demo 应如何选择

- 当前 16 米船应保留“小型船”的定位。它不应该因为几根高桅杆在镜头里显得壮观，就被按大型远洋战舰使用。
- 当前仅 4 个战斗人物仍会卡住，已有多人运动缺陷是主因之一；不能用“船小”解释掉实际寻路错误。
- 若 Demo 要展示 4 名己方加 6–8 名敌人的更完整遭遇，建议选择约 22–26 米、宽约 7–8 米的中型船设计。这个规模和队伍数是提案，不是本轮已确认扩展。
- 大船需要重新安排舱室、炮位、开口、台阶和甲板通路。整体放大现有模型会同时把栏杆、门洞、炮架放大，不能作为完整的船型升级。
- 先为角色建立比例尺，再核对门洞、栏杆、跳板、桅杆底座。至少一条贯通甲板的主通道需要允许角色按玩法要求通过和让行；具体宽度由角色碰撞与动作展开实测决定。
- 大船战斗镜头围绕当前交战区域移动，可切总览；无需为了同时装下整艘船而把人物缩得无法辨识。人物身高、碰撞与屏幕显示大小分开控制。

## 5. 海况应由独立因素共同驱动

至少分开组织：风向／风力、波向／波幅／波长、降雨强度、水面流向、湿润程度、能见度和天空照明。雨势大并不自动等于波浪大，近岸遮蔽水域也不应与外海拥有完全相同的波形。

| 评审情境 | 海面与泡沫 | 船／岸／天气需要同步的表现 |
| --- | --- | --- |
| 港内或避风处 | 小尺度涟漪、稳定深浅、轻微倒影扰动 | 船体轻晃、岸边接触、港内航迹较克制 |
| 外海轻风 | 缓慢大尺度起伏叠加细波，亮面有疏密，尾迹依航速展开 | 帆、旗、烟和喷溅具有一致的风向关系 |
| 起风、有浪 | 波峰与波谷有形体，少量白沫随波峰生成；船首破浪与船侧流动明显 | 船体俯仰／横摇、帆受风、旗帜和炮烟偏移协调，镜头和 HUD 保持稳定可读 |
| 下雨、浪不大 | 雨落水的短纹理、水滴扰动，天空与水面明度下降 | 甲板／岸地变湿、积水出现、滴水；遮蔽区和露天区有区别 |
| 风雨较大 | 浪、白沫、喷溅、雨和能见度共同变化，仍能读出船和炮击 | 湿润、风向、帆态、倒影与照明一致；危险区域和选中目标仍清楚 |

这些是需要验证的画面情境，不是本轮授权扩成完整气象模拟。风雨如何影响命中、船速、人物行动属于后续玩法决定，不能在做视觉效果时悄悄加入数值惩罚。

### 实现约束

- 水面几何起伏负责大形，法线与绘制纹理负责细波；减少重复平行亮条，远处降低细节频率。颜色与笔触保持 v03。
- 船边接触泡沫要断续流动，船首分水由相对水速和航向驱动，侧流向后脱离；不能把发白的完整轮廓永远钉在船体上。
- 尾迹保留世界空间轨迹，按速度、转弯、时间变化宽度和破碎程度。停船后继续消散；风浪大时允许尾迹被环境波纹逐渐打散。
- 风向应同时影响帆／旗、炮烟、雨线与喷溅，但远处涌浪方向不必被强制等同当前局部风向。天气变化采用平顺过渡，不能突然替换整片海。
- 海水高度变化后，船体浮动、炮弹触水、水花落点与波纹扩散必须参考同一套水面状态。当前固定 y=0.18 的触水判断需要在未来改水体时一起评估，避免弹体落到旧平面才出水花。
- 各天气下分别评审直航、转弯、减速／停船、炮击命中／擦过／落水；保留正常速度片段，不能只用静帧或慢镜头证明效果。

## 6. 下一阶段验收顺序

1. 先确定当前使用小船还是换为中型船，并给出同尺度人物、船型、可走区域及期望人数的可视化对照。
2. 修复既有多人接敌问题，以确定真实有效空间；把路径／布阵提示的数据与移动统一。
3. 完成游戏 UI 整屏美术稿、角色独立半身和关键控件状态图。图稿中使用真实内容长度与游戏镜头，不能只有布局线框。
4. 制作本地角色动作与图形 UI 资产，并接入正常操作的 Godot 场景；检验选中、移动、技能、伤害、无效操作和对白。
5. 单独完成同一航海镜头下的平静、起风、降雨／风浪对照，再合入整段故事。

尚未完成的 UI 美术稿、H3 动作、正式导航及风浪实机效果保持明确待办；不能将本轮尺度示意和参考研究称作这些内容已经交付。
