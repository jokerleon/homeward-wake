日期：2026-10-08。研究记录与建议，尚未制作本项目 Godot 场景，尚未批准新画风。

## 结论

本轮重点是让画面成立。建议把生产方式收敛到：**有明确绘制风格的二维人物/植物，与有体积的地形、建筑、船体组合，再统一镜头、材质尺度和光影。** 引擎和插件负责把这些素材正确地放在空间中；素材本身的轮廓、明暗与构图需要先达到目标。

FrameRonin 值得研究的是这一整套组合方式。NPC 资源接入、有限建筑参数化等核心功能可以独立实现；完整地形工具优先评估已有开源基础。不能因为工具使用过 AI，就推断它的预设库、美术和工程成熟度可以很快完整复制。

保留 MiniMax 流程是合理的；现有沈砚素材只作为可用候选和技术验证输入。它的细腻手绘风格与 FrameRonin 公开场景的明显像素笔触并不相同，不能把两者直接拼接后宣称风格统一。

## 1. FrameRonin 画面中真正值得学的部分

### 森林

![FrameRonin 作者公开的森林展示图，非本项目产物](https://frameronin.com/roninterr-showcase/images/showcase_forest_party.png)

图像来源：[Roninterr 公开展示](https://frameronin.com/roninterr-showcase/)。

从这张图能直接看到：人物所在的中景较亮、轮廓清楚；前景植物形成框景；远景树木通过雾、明度和对比下降分层。树冠不是均匀的绿色噪点，较大的叶簇、暗面和枝干先构成形体，小细节依附这些形体。人物与树木具有接近的绘制语言。

图中能看出明显的像素绘制轮廓；结合产品页对二维角色/植被与三维地形的说明，可以推断贴片素材在表现中承担了重要作用。仅凭图片不能证明每棵树的网格结构，也不能验证全方位旋转效果。

不建议照搬满地花草的密度。港口道路、甲板和战斗区域需要更安静的表面；密集细节应集中在林缘、墙脚和岸边等有用途的位置。森林图的前景景深也不能直接成为全游戏设置。

### 建筑

![FrameRonin 作者公开的武侠小镇展示图，非本项目产物](https://frameronin.com/ronin-building/assets/image-14-8dca48a798707ebe.png)

图像来源：[ronin建筑公开展示](https://frameronin.com/ronin-building/)。

屋顶、墙体、廊、楼梯先形成清楚体积；重复的材料和构件让不同建筑属于同一个家族。阴影强调檐下和接地，主体与远近景分离，人物尺度能和建筑互相参照。

仍能观察到重复树形、较空的广场、强景深和部分明暗较重的表面。这些不应自动变成我们的风格规定。网页称为“武侠”的预设，也不等于已经核验适合某个明代年代、地区和建筑用途。

### 现有 MiniMax 人物

![现有沈砚右向待机原帧，仅作流程与风格差异检查](../Assets/Characters/Library/ShenYan/fullset-v01/E/frames/idle/0000.png)

这份人物的细节、过渡和边缘偏细腻手绘。若环境采用明显的像素树、硬边低分辨率屋顶，人物可能像来自另一款游戏。下一轮要先统一画面里“能看见多细的笔触”和角色轮廓，再讨论纹理分辨率、缩放过滤与后处理。

**建议保留流程和动作资产的使用可能性，不把现有衣服、人物身份、288×288 画布或旧场景人物高度定为新项目标准。** 不在本轮擅自把全部人物像素化，也不新生成整套角色。

### 地形的更实用候选

[Terrain3D 作者说明](https://tokisan.com/terrain3d/) 与 [官方仓库](https://github.com/TokisanGames/Terrain3D) 提供可编辑地形、材质绘制、实例植被和 LOD，采用 MIT 许可，可作为未来底座候选。其公开能力与我们关心的地形需求重叠，因此没有必要为“复刻”先重写同类 C++ 地形系统。

这不证明 Roninterr 与 Terrain3D 存在具体代码关系，也不证明安装 Terrain3D 就会获得 FrameRonin 的画风。素材、材质、灯光和布置仍要由项目完成；与 Godot 4.7.2 的具体版本兼容需在实际采用时检查。

## 3. 本项目建议的美术实现方法

### 先锁定镜头中的结果

第一份视觉样片用一个港口局部：少量同族建筑、坡/台阶或码头高差、树木、岸水、一艘有体积的船和一个正常大小人物。前、中、远景同时出现，白昼下先成立。

先比较固定俯视镜头下的物体比例和绘制细节，不先支持任意旋转与无限缩放。人物源视频角度必须与镜头匹配；保留八方向移动不代表同一角色素材可以匹配任意相机俯角。

这只是后续样片建议，本轮没有创建该场景，也没有将其变成完整玩法制作的授权。

### 素材、几何、着色器各负责什么

| 视觉部分 | 建议职责 | 首次检验 |
| --- | --- | --- |
| 人物 | MiniMax 视频转帧；游戏决定位移、朝向和事件 | 衣服/脸稳定，接地，缩到游戏大小仍可辨认；左右攻击不抖动 |
| 树和灌木 | 先获得有明确轮廓与叶簇明暗的绘制素材；按镜头选择贴片、少量交叉面或必要主干体积 | 人物穿行时遮挡正确、树脚有接触，镜头变化不会露出不可接受的纸片感 |
| 建筑与船体 | 真三维主形承载屋顶、体积、廊与船身；风格化贴图承担大部分表面细节 | 轮廓与层级在普通缩放下可读，不依靠满面细碎几何 |
| 草土、铺地与岩岸 | 低频主色块、覆盖形状和少量高频材质；边界由画面组织与真实地形决定 | 草土不均匀铺满噪声；道路、岸线、崖面读得清楚 |
| 水 | 有主体的色面、浅深组织、稀疏有方向的波纹，配合船/岸接触 | 静态像水，运动中也像水；避免单一蓝带、全透明玻璃和均匀循环小亮点 |
| 光与后期 | 有方向的主光、环境补光、稳定接触阴影，随后少量雾/景深/辉光 | 关闭景深和辉光时，主体画面仍然成立 |

不能把一棵形状与笔触都不合格的树，靠“加像素滤镜”变成目标风格。也不能把材质不统一的问题全交给一个屏幕后处理解决。按相机中实际显示的细节大小选纹理，不要求所有物体使用同一贴图分辨率。

### Godot 中优先验证的具体环节

- **人物与植物的透明和遮挡**：比较 alpha cut/适当预通过与边缘处理，保留深度测试；真正半透明效果单独安排。不能依靠统一提高渲染优先级解决所有前后关系。[官方精灵说明](https://docs.godotengine.org/en/stable/classes/class_spritebase3d.html)、[透明排序限制](https://docs.godotengine.org/en/stable/tutorials/3d/3d_rendering_limitations.html)
- **明暗整合**：AI 人物已有明暗，先比较弱受光或受环境色调制的表现，避免再次施加过强光照。植物/人物投影需要实际看，不默认 billboard 自投影天然正确。
- **真实运行环境**：明确配置 WorldEnvironment 和场景灯光，不把编辑器临时预览太阳当成游戏灯光。[官方环境说明](https://docs.godotengine.org/en/stable/tutorials/3d/environment_and_post_processing.html)
- **细节在运动中的稳定性**：观察摄像机平移、缩放和船只转向中的边缘闪烁、拖影、透明排序与纹理重复。静态截图不能回答这些问题。
- **水的事实与外观**：水位、浅滩、船的位置来自场景/玩法数据；屏幕深度只参与显示。首份水样必须实际拍到水和船边接触。

Forward+ 是 Windows PC 首个测试候选，具体画质档由样片决定。景深并非只有 Forward+ 才能使用，官方说明它支持 Forward+ 和 Mobile；不能将某一教程的推荐渲染器误写成 HD-2D 的唯一实现条件。[渲染器对照](https://docs.godotengine.org/en/stable/tutorials/rendering/renderers.html)、[相机景深说明](https://docs.godotengine.org/en/stable/classes/class_cameraattributespractical.html)

## 4. 与海战、人物战斗的关系

船只火炮海战与人物近距离战斗是两种尺度，接舷会连接二者。可共用材质画法、颜色关系、灯光与海面，船体使用三维模型，船员继续使用二维角色。远距离要看得清航向、船型、炮火和损伤；近距离要看得清人物、武器、甲板通路与遮挡。

人物战斗是否保留战棋，或者改为两拨人马交战，仍然待定。现阶段不据此制作格子、回合条或完整战斗控制器。先确保这两个观看尺度下的美术语言一致。

## 6. 下一份画面怎样判断通过

1. 同一正常游戏镜头中，人物、建筑、植物、地面和水看起来属于同一个世界。
2. 白昼下也有前中远景、受光与接触关系；关闭强后期不会暴露成片的灰模感或贴纸感。
3. 角色大小、相机和素材角度匹配，建筑/树木遮挡可读，脚底稳定。
4. 原速录像包含人物走动、轻微镜头移动、水面与船体接触；没有明显闪烁、拖影和纸片穿帮。
5. 明确指出当前最弱的两三处，并提交可辨认的修改前后对照。颜色数值、面数和代码数量不替代判断。

先达到这份有限样片，再扩资产库、参数化工具和地图。复刻整套插件不是本项目启动的前提。
